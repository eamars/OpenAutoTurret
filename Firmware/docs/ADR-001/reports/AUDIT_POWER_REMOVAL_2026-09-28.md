# 断电清点：谁在拿掉(payload 的)电力，凭什么 (2026-09-28)

主人的规矩（原话摘要，09-28 中午）：

> 除非最紧急的错误（例如撞到 endstop），station 尽量不要出现断电。一旦断电，payload 是
> 不平衡负载，掉下来撞 endstop 本身造成的伤害比不断电大得多。**断电是最后手段，不是可以
> 随便发生的事。** 并且：「代码里应该还有不少类似的问题。我需要你找出来，然后改掉，或者删掉。」

判据（我自己给的，可反驳）：一条**会拿掉电力/锁死轴**的判据，只有满足以下之一才配存在 —
①不满足就**无法控制**这条轴（看不见它、或没在跟它说话）；②motor 自己报告**它会伤自己**（过温）；
③继续走的**可预见后果**比断电更糟（撞硬界）。**"某个读数看起来不像话"不属于任何一条。**

先记一条被清掉的历史论据：**滑环没有限制**（主人今天确认，自由移动、不需要计圈数）——
所以无限制 yaw 不再有任何机械/线缆理由，凡以"线缆会绕"为名的保守都可以重新审。

## ① 唯一的集中点：`MixedCanMotorBackend` 的 yaw 守卫（`mixed_can_motor_backend.cpp:447`）

`should_stop` 是一串 **OR**，任何一种为真就 **latch**：发零 + 锁死 + 只能重启进程
（`recover_motors` → `RECOVERY FAILED: motor recovery unsupported by this backend`，
GM6020 反馈帧里没有故障清除位）。**扁平的 latch 把所有严重度当成同一件事处理**——这就是
那类"本来不需要 crash 的场景被理解错误变成了 crash"的**结构根因**，比单条判据更值得改。

## ② 结构性缺口：这个后端上 **latch 不可解**

今天最贵的不是哪一条判据，是**没有回头路**：`recover_motors` 直接回 `unsupported`，
于是一帧 CAN 错、一次我们自己的 NaN、一次被误判的静止 = **人工重启**。
而断电代价 = payload 自由落体撞硬界。**建议（下一条就做的）**：
把 latch 分成 **自清类**（#3/#4/#5/#8/#9：条件消失即恢复）与 **不可自清类**（#1/#2/#7：必须人来看），
自清类带**次数预算**（一段时间窗内最多 N 次，超了就锁住要人看），防振荡。
`recover_motors` 在两类的回答应当不同，且**答案可测**（纯函数 `latch_verdict(conditions)`）。
