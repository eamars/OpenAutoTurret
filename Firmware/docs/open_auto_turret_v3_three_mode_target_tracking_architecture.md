# OpenAutoTurret v3
## Three-Mode Controller, Target Selection, Auto Tracking, Auto Roaming, and Manual Control

**Document status:** Implementation handover / target-state architecture  
**Version:** 3.0  
**Date:** 2026-09-03  
**Depends on:** OpenAutoTurret v1 software/control architecture  
**Assumption:** v1 is fully implemented and validated before this work begins.  
**Compatibility:** The BNO085/IMU expansion and operator-first web UI may be present, but neither is a blocker for the core v3 controller.  
**Scope:** Non-weaponized pan/tilt camera/sensor tracking platform.

---

# 1. Purpose

v1 established the safe deterministic motion foundation:

- Raspberry Pi 5 host;
- IMX500 camera pipeline;
- CyberGear yaw/pitch direct drive;
- SocketCAN motor ownership;
- mechanical homing;
- host logical joint coordinates;
- soft limits and braking envelope;
- jerk/acceleration/velocity constrained trajectory generation;
- timestamp-aligned camera measurements;
- target line-of-sight estimation;
- hold/search concepts;
- safety supervisor;
- web/telemetry isolation.

v3 turns that foundation into a complete operator-usable controller with exactly three primary operating modes:

```text
MANUAL
AUTO_TRACK
AUTO_ROAM
```

At the end of v3 the operator shall be able to:

1. see candidate targets in the camera view;
2. select a specific target;
3. enter `AUTO_TRACK`;
4. have the selected target followed automatically whenever it is seen;
5. have the controller safely stop/hold if that target is lost;
6. have tracking automatically resume if the selected target is reacquired;
7. enter `AUTO_ROAM` and have the camera autonomously scan the configured safe field of regard;
8. enter `MANUAL` and jog/step/position the turret with real-time yaw/pitch feedback;
9. switch among all three modes without bypassing the existing v1 safety and trajectory layers.

`HOLD`, `TRACKING`, `COASTING`, `SEARCH_SWEEP`, `JOGGING`, `PARKING`, etc. become **controller phases/substates**, not primary user modes.

# 2. Frozen v3 operating-mode model

The user-facing mode enum shall be:

```cpp
enum class OperatingMode {
    MANUAL,
    AUTO_TRACK,
    AUTO_ROAM
};
```

Do not continue using `HOLD`, `TRACK`, and `SEARCH` as three peer user modes.

Instead:

```text
MANUAL
    HOLD
    JOG
    STEP
    GOTO

AUTO_TRACK
    WAIT_TARGET
    ACQUIRE
    TRACK
    COAST
    LOST_HOLD
    REACQUIRE

AUTO_ROAM
    INIT
    SWEEP
    TURNAROUND
    STEP_ELEVATION
    HOLD
```

Safety/calibration states remain above operating modes:

```text
BOOT
UNHOMED
HOMING
CALIBRATING
READY
PARKING
FAULT
```

A safety state can override any operating mode.

# 3. Key behavioral decision

## 3.1 AUTO_TRACK

`AUTO_TRACK` means:

> Track the currently selected target automatically whenever the selected target is confidently visible.

If the selected target is not currently visible:

- do not roam the turret looking for arbitrary targets;
- briefly continue prediction if appropriate;
- brake to a safe hold;
- continue processing camera detections;
- automatically resume tracking when the selected target is confidently reacquired.

This directly satisfies:

```text
selected target + AUTO_TRACK + target seen
    -> automatically track
```

## 3.2 AUTO_ROAM

`AUTO_ROAM` means:

> Autonomously scan the configured safe field of regard using a deterministic safe roaming pattern.

Default v3 policy:

```text
AUTO_ROAM does not automatically pursue a selected/detected target.
```

It may still:

- display detections;
- maintain candidate tracks;
- preserve the operator's selected target;
- notify the UI that the selected target is visible.

But motion continues to be generated by `RoamPlanner` until the user explicitly changes to `AUTO_TRACK`.

Future extension:

```text
ROAM_AND_ACQUIRE
```

may be added later as a policy, but it is not part of the v3 minimum target state.

## 3.3 MANUAL

`MANUAL` means:

> All normal motion is initiated explicitly by the operator.

Manual includes:

- hold;
- dead-man jog;
- fixed-angle step;
- optional point-and-go on the travel map;
- park/home requests through the existing supervisory state machine.

No camera detection causes motion in MANUAL.

# 6. Multi-object tracking is required for target selection

A detector alone is not sufficient for a useful target selector.

IMX500 MobileNet SSD may report:

```text
person
bbox
confidence
```

on each frame, but the UI needs a stable identity such as:

```text
Person #1
Person #2
```

across consecutive frames.

Therefore v3 adds a lightweight multi-object tracker in `visiond`.

# 7. `TrackManager`

## 7.1 Responsibilities

`TrackManager` shall:

- receive all detections from each IMX500 frame;
- associate detections with existing tracks;
- create new tracks;
- age missing tracks;
- maintain image-plane position/velocity prediction;
- publish stable runtime `track_uuid`;
- provide confidence and visibility state;
- optionally maintain a lightweight appearance descriptor for reacquisition.

## 7.2 Initial implementation

A v3 implementation does not require a heavy deep re-identification model.

Recommended initial association:

```text
class compatibility
+
predicted centroid distance
+
IoU
+
bbox scale consistency
```

Use:

- per-track constant-velocity Kalman filter;
- Hungarian assignment or equivalent minimum-cost matching;
- gating to reject implausible associations.

## 7.3 Optional appearance signature

For stronger short-term reacquisition, add a cheap appearance signature from the image crop, for example:

- HSV/RGB color histogram;
- coarse spatial color histogram;
- small feature vector from an inexpensive CPU model if profiling permits.

Architecture:

```text
AppearanceDescriptorProvider
```

shall be optional.

Do not make v3 depend on strong person re-identification.

# 8. Track states

Suggested:

```cpp
enum class TrackState {
    TENTATIVE,
    CONFIRMED,
    OCCLUDED,
    LOST
};
```

Rules:

### TENTATIVE

New detection.

Require a configurable number of consistent frames before it becomes selectable.

### CONFIRMED

Stable candidate.

May be selected.

### OCCLUDED

Detection temporarily missing but track prediction still valid.

May be eligible for selected-target coast/reacquire.

### LOST

Track has exceeded the allowed missing interval.

Retain a descriptor for a configurable reacquisition window, then retire.


- brighter outline;
- selected/lock icon;

Preferred:

```text

    ->

    ->
```


# 12. Target selection is independent from mode

Selection state persists independently from operating mode.

Example:

```text
selected_target = Person #1

mode = MANUAL
    -> no automatic motion

mode = AUTO_ROAM
    -> no automatic pursuit

mode = AUTO_TRACK
    -> automatically follow Person #1 when visible
```

This is important.

Do not clear target selection merely because the operator switches modes.

Provide an explicit:

```text
Clear target
```

command.

# 16. AUTO_TRACK entry behavior

When mode changes to:

```text
AUTO_TRACK
```

### Selected target visible

Immediately enter:

```text
ACQUIRE -> TRACKING
```

using normal v1 trajectory constraints.

### Target selected but not visible

Enter:

```text
WAIT_TARGET
```

The turret holds safely.

If the same target becomes visible:

```text
WAIT_TARGET -> ACQUIRE -> TRACKING
```

automatically.

### No target selected

Remain:

```text
WAIT_TARGET
```

and show:

```text
Select a target
```

No autonomous motion.

Default:

```text
bbox center
```

but keep the v1 configurable anchor abstraction.

For a person, future options may include:

- upper torso;

# 19. AUTO_TRACK target confidence

The controller shall not chase every weak association.

Compute:

```text
selected_target_confidence
```

from:

- detector confidence;
- track continuity;
- association quality;
- track age;
- reacquisition score.

Suggested states:

```text
HIGH
MEDIUM
LOW
INVALID
```

Motion limits may be scaled:

```text
HIGH:
    normal configured tracking v/a/j

MEDIUM:
    modest derating

LOW:
    do not accelerate aggressively

INVALID:
    coast/hold
```

# 20. Lost-target behavior

Use explicit timing parameters.

Example conceptual values only:

```text
coast_ms             250–400
lost_hold_ms         after coast
reacquire_window_ms  2000–5000
```

Actual values are commissioning/configuration.

## 20.1 COASTING

Continue v1 target-state prediction briefly.

Simultaneously reduce permitted acceleration as uncertainty grows.

## 20.2 LOST_HOLD

Stop predicting motion into the future.

Generate:

```text
controlled brake -> hold
```

Continue vision processing.

## 20.3 Automatic resume

If selected target is confidently reacquired:

```text
LOST_HOLD -> REACQUIRE -> TRACKING
```

No user click is required.

---

# 21. Reacquisition rules

A specific selected target must not silently become another object of the same class.

Reacquisition score can combine:

```text
class
predicted image location
predicted bbox scale
recent motion
appearance descriptor
time since last seen
```

Require:

```text
score >= reacquire_threshold
```

and sufficient margin over the next-best candidate where practical.

If ambiguous:

```text
remain LOST_HOLD
```

and ask the operator to reselect.

Safety/user trust is more important than forcing a match.

---

# 22. Track retirement

After:

```text
reacquire_window
```

expires without a confident match:

```text
selection visibility = STALE
```

The selection may remain displayed as:

```text
Person #1 — lost
```

but `AUTO_TRACK` holds.

Operator can:

- wait;
- reselect;
- clear target;
- change to AUTO_ROAM.

Future appearance/re-ID work may extend reacquisition time.

---

# 23. Switching selected targets during AUTO_TRACK

If the operator selects another visible target while already tracking:

1. `TargetSelectionManager` atomically changes selection.
2. Old target motion intent becomes invalid.
3. New selected LOS enters `AutoTrackController`.
4. Existing v1 trajectory generator smoothly redirects.

Do not:

- stop motor abruptly;
- jump raw motor setpoint;
- let both targets compete.

# 27. STOP MOTION behavior

The UI needs a prominent:

```text
STOP MOTION
```

v3 semantics:

```text
cancel active autonomous/manual intent
    ->
existing v1 controlled brake
    ->
switch OperatingMode to MANUAL
    ->
MANUAL/HOLD
```

This prevents an autonomous mode from immediately restarting motion on the next cycle.

Do not confuse STOP MOTION with:

- motor disable;
- emergency power removal;
- safe shutdown.

```text
RoamPlanner
```

Responsibilities:

- choose safe scan targets;
- respect configured roam envelope;
- keep adequate braking margin;
- smoothly reverse direction;
- avoid unreachable joint combinations;
- optionally use world-horizontal/level compensation when IMU is valid.


Implement one deterministic pattern first:

```text
BOUNDED SWEEP
```

Example:

```text
left roam boundary
    ->
smooth yaw sweep
    ->
right roam boundary
    ->
smooth turnaround
    ->
left boundary
```

Pitch/elevation remains at:

```text
roam_pitch_reference
```

or, if IMU/world-level support is valid:

```text
roam_world_elevation
```

This is sufficient to complete v3.

# 31. Optional v3 roaming pattern: raster

After simple sweep is validated, add:

```text
RASTER
```

Concept:

```text
pitch/elevation band 1:
    left -> right

step pitch

band 2:
    right -> left

step pitch

...
```

Use a boustrophedon pattern to avoid unnecessary full resets.

All waypoints must be inside the v1 safe/collision envelope.

---

# 32. Roam envelope

Do not automatically use the full soft-limit envelope.

Define an inner application envelope:

```text
roam envelope
    ⊂
safe motion envelope
    ⊂
mechanical range
```

Reasons:

- leave braking reserve;
- avoid continuous operation near mechanical extremes;
- avoid unnecessary payload/cable stress.

Config:

```text
roam_yaw_min
roam_yaw_max
roam_pitch_min
roam_pitch_max
```

or a polygon/coupled envelope.

---

# 33. Roam with BNO085 available

If the BNO085 expansion is valid:

Default preferred yaw scan:

```text
world-level yaw
```

The pitch axis automatically compensates installation tilt.

If IMU gravity is invalid:

```text
fallback to configured joint-space pitch
```

according to existing IMU fallback policy.

IMU is not required for AUTO_ROAM.

# 34. Roaming and target detection

During AUTO_ROAM:

- `visiond` continues detection;
- `TrackManager` continues tracking;
- target selector remains usable;
- selected target visibility remains visible in UI.

But default motion policy remains:

```text
RoamPlanner owns motion.
```

If the operator wants to pursue the visible selected target:

```text
switch to AUTO_TRACK
```

This keeps mode semantics unambiguous.

# 36. AUTO_ROAM entry behavior

On mode switch to `AUTO_ROAM`:

1. cancel old mode intent;
2. use current actual/planned state as trajectory start;
3. initialize roam direction based on nearest sensible sweep direction;
4. do not jump to a distant scan-start position unnecessarily;
5. begin smooth scan.

This makes mode switching feel continuous.

# 40. Manual joint versus level frame

If BNO085 expansion is available:

```text
MANUAL frame:
    JOINT
    LEVEL
```

`JOINT`:

- left/right change yaw joint;
- up/down change pitch joint.

`LEVEL`:

- horizontal jog requests world-level yaw;
- v1.1 world-level constraint generates pitch compensation.

If IMU invalid:

```text

```

and UI explains why.

Core v3 works in JOINT mode without IMU.

# 44. Mode transition rules

## MANUAL -> AUTO_TRACK

Allowed when:

- position valid;
- no blocking safety fault.

A selected visible target is not required.

If target visible:

```text
ACQUIRE
```

If not:

```text
WAIT_TARGET
```

## MANUAL -> AUTO_ROAM

Allowed when:

- position valid;
- roam envelope valid;
- safety healthy.

## AUTO_TRACK -> MANUAL

Immediately invalidate tracking intent and:

```text
controlled brake -> MANUAL/HOLD
```

unless operator simultaneously supplies a valid manual destination that can be transitioned to safely.

Simpler initial implementation: brake/hold first.

## AUTO_ROAM -> MANUAL

Same.

## AUTO_ROAM -> AUTO_TRACK

If selected target visible:

```text
smoothly redirect to target
```

If not:

```text
stop roam -> WAIT_TARGET/HOLD
```

## AUTO_TRACK -> AUTO_ROAM

Invalidate target motion intent.

RoamPlanner initializes from current pose.

Selection is preserved.

# 54. Control-loop pseudocode

```text
loop every CONTROL_PERIOD:

    now = monotonic_time()

    axis = motor_state_snapshot()

    update_v1_health_and_safety()

    # camera/track data
    if new_track_set:
        track_registry.update(track_set)

        target_selection_manager.update_visibility(
            track_registry,
            now
        )

        if selected_target_observation_is_new:
            historical_pose =
                motor_history.interpolate(
                    observation.sensor_timestamp
                )

            if historical_pose.valid:
                los =
                    camera_and_kinematics.to_base_los(
                        observation,
                        historical_pose
                    )

                target_estimator.measurement_update(
                    observation.sensor_timestamp,
                    los,
                    observation.track_confidence
                )

    target_estimator.predict_to(
        now + actuation_horizon
    )

    mode_manager.update(now)

    switch mode_manager.mode:

        MANUAL:
            intent = manual_controller.compute(
                now,
                axis,
                manual_command_state
            )

        AUTO_TRACK:
            intent = auto_track_controller.compute(
                now,
                target_selection_manager,
                target_estimator,
                axis
            )

        AUTO_ROAM:
            intent = roam_planner.compute(
                now,
                axis,
                safe_envelope
            )

    reference =
        reference_manager.resolve(intent)

    safe_reference =
        safety_envelope.constrain(
            reference,
            axis,
            calibration,
            collision_envelope
        )

    trajectory =
        trajectory_generator.step(
            safe_reference
        )

    safety_supervisor.verify(...)

    apply_safety_override_if_required()

    motor_adapter.send(trajectory)

    publish_telemetry_nonblocking()
```

---

# 55. AUTO_TRACK pseudocode

```text
if no selected target:
    state = WAIT_TARGET
    return HOLD

visibility =
    target_selection.visibility

if visibility == VISIBLE:

    if state in [
        WAIT_TARGET,
        LOST_HOLD,
        REACQUIRE,
        COASTING
    ]:
        state = ACQUIRE

    if selected confidence >= minimum_track_confidence:
        state = TRACKING

        return LOS_DIRECTION(
            target_estimator.predicted_los,
            confidence_scaled_limits
        )

    else:
        return cautious HOLD/COAST

if visibility == OCCLUDED:

    if age_since_seen < coast_timeout:
        state = COASTING

        return LOS_DIRECTION(
            short_horizon_prediction,
            progressively_derated_limits
        )

state = LOST_HOLD

return HOLD
```

# 56. AUTO_ROAM pseudocode

Simple sweep:

```text
if entering AUTO_ROAM:
    initialize direction from current yaw
    define current roam elevation/pitch

if not at current boundary:
    request boundary target

else:
    smoothly reverse direction

if IMU level frame valid:
    intent = WORLD_LEVEL_YAW(
        yaw_target = boundary,
        elevation = roam_world_elevation
    )
else:
    intent = JOINT_POSITION(
        yaw = boundary,
        pitch = configured_roam_pitch
    )

return intent
```

The trajectory generator handles the smooth motion.

- [ ] Controller scans a configured safe envelope autonomously.
- [ ] Turnarounds are acceleration/jerk constrained.
- [ ] Roam region remains inside v1 safe envelope.
- [ ] Detections continue while roaming.

- [ ] Lost browser/keepalive stops jog.

- [ ] Step move works.

- [ ] Requested/reference/actual motion is visible to operator.

## COMMON

- [ ] Exactly one normal operating mode owns motion at a time.
- [ ] STOP MOTION always results in MANUAL/HOLD.
- [ ] Safety/homing/park states override all operating modes.
- [ ] No UI/vision process can write motors directly.
- [ ] Existing v1 control-loop timing remains within accepted limits.
- [ ] All mode changes and target changes are logged.

# 111. Frozen v3 architectural decisions

Unless implementation profiling demonstrates a concrete problem:

1. **The final user operating modes are `MANUAL`, `AUTO_TRACK`, and `AUTO_ROAM`.**
2. **HOLD/TRACKING/COASTING/etc. are phases, not peer user modes.**
3. **Target selection is persistent and independent of operating mode.**
4. **AUTO_TRACK automatically follows the selected target whenever it is confidently visible.**
5. **AUTO_TRACK does not actively roam when the selected target is absent.**
6. **AUTO_TRACK briefly coasts/predicts, then brakes to hold.**
7. **AUTO_TRACK automatically resumes after confident reacquisition.**
8. **AUTO_ROAM does not automatically pursue targets by default.**
9. **AUTO_ROAM uses a deterministic bounded sweep as the required v3 pattern.**
10. **MANUAL uses dead-man jog and bounded step/position requests.**
11. **STOP MOTION switches the controller to MANUAL/HOLD.**
12. **`visiond` performs multi-object track association and publishes a TrackSet.**
13. **`controld` owns target selection and all motion authority.**
14. **The UI selects a `track_uuid`, not raw motor coordinates.**
15. **Track ID association begins lightweight; strong re-identification is optional.**
16. **Ambiguous reacquisition results in hold rather than target stealing.**
17. **All three modes emit a common `MotionIntent` into the existing v1 reference/safety/trajectory path.**
18. **The v1 braking, limits, homing, and motor-control architecture remains unchanged and authoritative.**
19. **BNO085 level/world motion is an optional enhancement, not a v3 dependency.**
20. **The operator UI is mode-aware and target selection is primarily video-overlay based.**

# Appendix C — Why AUTO_TRACK and AUTO_ROAM remain separate

Combining them into one “automatic” mode creates ambiguous behavior:

```text
If target disappears:
should the turret remain still?
should it search?
how far should it search?
should it follow any person?
should it return to scan?
```

v3 avoids this ambiguity.

`AUTO_TRACK`:

```text
selection-driven
```

`AUTO_ROAM`:

```text
scan-plan-driven
```

The operator can change mode explicitly in one action.

A future policy can combine them once desired behavior is defined.
