## 已发现的执行方法问题

- **没有先固定实验设计和停止准则。** 我逐轮阅读文字输出再挑参数，造成多次 SSH、复制、解析和推理；机械执行虽脚本化，决策仍高度串行。
- **起动指标不能代表持续运行。** 三编码器计数约 0.132°；很快达到这个阈值，后面仍可能基本不动。我继续逐档提高 Kp，而没有先充分隔离起动、连续匀速、保持偏置和制动的成因。
- **补偿开关试验存在混杂因素。** 从关闭切到启用时，不只增加 0.05 A；启用路径还包含新运动意图时的积分处理、补偿状态切换和最终输出 slew。因此起动变快不能全部归因于“测得了摩擦补偿”。
- **补偿候选不是已辨识参数。** 0.05 A 是基于前期有向输出观测选的小试验值，0.2 A 是后续探索候选。此前运动和保持总电流都可在约 0.5 A，不能把总电流直接等同摩擦。没有完成有效的方向性摩擦分离和稳健上沿估计。
- **发生了参数应用失败后仍启动下一组脚本的编排错误。** 首次 Kp=2 被静止条件拒绝，但下一条测试命令仍执行，文件夹叫 `kp2-fine`，实际是 Kp=1。随后依据实际 trace 明确纠正，并在 `kp2-confirmed-fine` 重测。根因是主 agent 没有对依赖操作严格实行“应用成功才运行试验”。
- **IMU 取证起初不完整。** 初次复制的是仅保留约 11 秒的末尾文件，与之前运动不重叠，无法验证运动。之后增加只读归档器持续保留已有 IMU 数据，才取得重叠证据；这是可以提前避免的返工。
- **早期离线分析出现过误读。** 曾混淆 waypoint 的 `vref` 和实际内环输入 `be_cmd`，并误判 raw encoder 与位置关系；后来校正。当前 leased jog 路径明确使用手动速度，低 `vref` 不能解释恒定 `be_cmd=3°/s` 下的物理速度不足。
- **源码实现与实机参数选择同时推进。** PR3 集成和 PR4 准备与 PR2 调试交错；多次头文件修改触发广泛重编译，完整测试又暴露停车路径问题，增加上下文和构建开销。
- **曾错误选择在 Pi 编译。** 用户明确纠正后，已改为 WSL 原生测试和 ARM64 交叉编译。此次报告所列 `bad742d` 在 WSL 构建，Pi 只接收二进制、运行测试及实机程序。

这些问题由主 agent 的执行方式负责。现有资料不能准确拆分已耗 token 到每个步骤，因此不提供猜测的 token 数字。
